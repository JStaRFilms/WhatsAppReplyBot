# FR-002: Owner-command assistant conversation

## Requirement

Keep owner instructions in a separate assistant conversation. Support
unanswered-message review and drafting for a named contact without turning
incoming contact content into commands.

This is a MUS v1 requirement. Its product behavior is planned, not verified
by this documentation task.

## Acceptance

- Ambiguous names return candidate contact IDs for owner selection. Never guess
  from display name, phone text or model confidence.
- Model proposals for send, permission change, delegation or resume require
  exact authenticated one-use owner confirmation. Confirm hashes, versions and
  five-minute proposal expiry.
- Incoming text, quotes, attachment interpretation and memory cannot confirm
  actions, grant permissions or impersonate the owner.
- A send proposal returns an outbox ID only after confirmation and fresh
  validation. Reused request IDs with conflicting payloads return 409.
- An explicit draft request may address an unselected or never-reply contact,
  but exclusions deny AI access and never-reply still denies assistant
  delivery.

## Contracts

assistant_turns and owner_actions; POST assistant/turns, owner-actions and
owner-actions/{id}/confirm. Model decision object never includes executable
permission tools.

Use [Assistant_Architecture.md](../features/Assistant_Architecture.md) as the
shared schema and API/event contract. See the
[requirements index](../Project_Requirements.md) for scope and precedence.

## Verification

Use fake assistant responses for ambiguous targets, malicious inbound
instructions, proposal expiry/hash mismatch and stale confirmations. Paid model
behavior remains unverified until a separate approved test.

The evidence gates and test matrix are in
[Verification_Plan.md](../Verification_Plan.md). No live test is authorized
by this issue.

## Out of scope

General tool runtime, multi-agent system, calendar writes and implicit
permission changes.
