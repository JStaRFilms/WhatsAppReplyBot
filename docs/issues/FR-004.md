# FR-004: Approval workflow and fresh authorization

## Requirement

Provide approval decisions for pending drafts without treating approval as
permanent permission. Validate again immediately before transport handoff.

This is a MUS v1 requirement. Its product behavior is planned, not verified
by this documentation task.

## Acceptance

- Support approve, edit, dismiss, needs_owner and approve_with_follow_up.
  Editing produces a new pending revision, never sends automatically.
- Approve validates revision, trigger ID, workflow/policy versions, current
  mode, hours, control and grant. Revalidate at dispatch.
- New inbound content, takeover or policy change makes prior work stale. Stale
  drafts stay inspectable but cannot send without regeneration.
- Never-reply blocks assistant approval sends. approve_with_follow_up requires
  auto_reply plus a separately confirmed active bounded grant; it cannot change
  mode.
- Sent edits carry owner_edited_assistant authorship. Ordinary approval
  authorizes only the exact action and does not resume manual control.

## Contracts

drafts revision/state/action_json, owner_actions and outbox. POST
drafts/{id}/decision returns pending revision or actual outbox state.
draft.changed and needs_owner events.

Use [Assistant_Architecture.md](../features/Assistant_Architecture.md) as the
shared schema and API/event contract. See the
[requirements index](../Project_Requirements.md) for scope and precedence.

## Verification

Offline cases exercise all decisions, stale model completions, concurrent
policy changes, revision conflicts, follow-up denial and pre-handoff
revalidation.

The evidence gates and test matrix are in
[Verification_Plan.md](../Verification_Plan.md). No live test is authorized
by this issue.

## Out of scope

Automatic approval, silent action rewrites, screen layout and open-ended
follow-up.
